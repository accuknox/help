Identities hold

Every cloud account collects users, roles and keys faster than a team reviews them. The unused access stays live, and an attacker who takes one identity gets all of it.

02
Root causes

Access grows by default
and shrinks by hand

Machines outnumber people
Microsoft counts one human identity for every 10 workload identities. Each pipeline, function and service account gets a role, and few of those roles have a named owner.
Old identities stay active
A role built for a proof of concept keeps its policies after the project ends. Microsoft reported an average of 80% of workload identities inactive in 2023. An inactive identity keeps every permission it holds.
Groups hide the real grant
A user inherits every policy from every group it joins. A review of the policies attached to the user alone misses the rest, and a policy name says nothing about its statements.
Kubernetes has its own identities
Service accounts, roles and role bindings live inside the cluster. A cloud IAM review never reads them, so a ClusterRole that grants secrets access goes unseen.

Sources: Microsoft, 2024 State of Multicloud Security Risk Report, microsoft.com. Microsoft Entra blog, 2023 State of Cloud Permissions Risks report, techcommunity.microsoft.com.

04
Practice 01

You cannot cut access
you never listed

One list of every user, group and role across AWS, GCP, Azure and OCI, each tagged human or machine.

CIEM identity list with the cloud provider filter. help.accuknox.com/getting-started/ciem-onboarding

Do
  • Onboard every cloud account with the CIEM toggle on. It is on by default in Step 2 of 3.
  • Filter by Identity Type to count users, groups and roles per account.
  • Review machine identities as closely as people. A CI/CD account is a machine identity.
  • Give every identity a named owner before you change its access.
Don't
  • Don't inventory one cloud and assume the others match.
  • Don't treat service roles as background noise. In the demo account, 637 of the identities are roles.
  • Don't trust a spreadsheet of approved accounts as your inventory.

05
Practice 02

Remove the identity
nobody has used

An idle identity keeps every permission it holds. Check Days Since Last Used and start with the highest value.

CIEM lifecycle columns. help.accuknox.com/getting-started/ciem-overview

Do
  • Set an idle limit, such as 90 days, and flag every identity past it.
  • Use Created By to find the person who can confirm an identity is still needed.
  • Compare Age In Days with Last Used. An old identity used once is a removal candidate.
  • Move AWS IAM users with access keys to roles with temporary credentials.
Don't
  • Don't delete a machine identity before you check what calls it.
  • Don't keep a proof of concept role after the project closes.
  • Don't read 0 days as safe. A value of 0 means the identity ran today, with all its policies.
How AccuKnox closes the gap

CIEM shows Age In Days, Created By, Last Used and Days Since Last Used for each identity, and the Raw Information tab holds the same fields as JSON. Read the CIEM overview

06
Practice 03

Fix the identities that
can escalate first

Datadog found 2.4% of EC2 instances can reach full admin through privilege escalation. Rank identities by what their policies allow.

Risk class chips in the CIEM identity list. help.accuknox.com/getting-started/ciem-overview

Do
  • Work Privilege Escalation identities first, then Credentials Exposure and Data Exfiltration.
  • Open the +1 or +2 chip. One identity often carries several risk classes.
  • Use Total Findings by severity to order identities with the same risk class.
  • Check groups as well as users. A group with Privilege Escalation passes it to every member.
Don't
  • Don't sort only by identity count. One admin group outweighs 50 idle roles.
  • Don't ignore Infrastructure Modification on a machine role.
  • Don't close a risk class by renaming the policy. Change its statements.
How AccuKnox closes the gap

CIEM calculates risk classes from each identity's attached policies, such as Privilege Escalation, Data Exfiltration, Credentials Exposure and Infrastructure Modification. See how risk classes work

Source: Datadog, State of Cloud Security, October 2025, datadoghq.com.

07
Practice 04

Read the policy,
not the policy name

A wildcard action hides behind a harmless name. Expand the policy and read every statement.

Policy Attached, with an inline policy expanded to JSON. help.accuknox.com/getting-started/ciem-overview

Do
  • Search every statement for a wildcard in Action or Resource.
  • List inline policies separately. An inline policy lives on one identity and escapes shared review.
  • Prefer user managed policies your team versions over copies pasted inline.
  • Recheck cloud managed policies after the provider updates them.
Don't
  • Don't approve a policy from its name alone.
  • Don't attach a FullAccess policy to fix one failed call.
  • Don't leave an inline policy on a user after the user changes teams.
How AccuKnox closes the gap

The Overview tab lists each attached policy with its type, cloud managed, inline or user managed, and expands it to the full JSON document. Open an identity overview

08
Practice 05

Follow access through
every group

The access graph draws the chain from an identity through its groups to each policy it inherits.

CIEM access graph of one demo AWS user. help.accuknox.com/getting-started/ciem-overview

Do
  • Open the Access Graph for every user in an Admin group or a FullAccess group.
  • Remove a user from a group when one policy in that group is the only one it needs.
  • Use Related Identities to find others in the same account with the same pattern.
  • Recheck the graph after each group membership change.
Don't
  • Don't review only the policies attached straight to a user.
  • Don't add a person to an admin group for one task.
  • Don't let groups pile up. Merge groups that grant the same policies.
How AccuKnox closes the gap

The Access Graph reads top to bottom: the identity, its groups, and the policies each group grants. A policy attached straight to the identity sits beside the groups. Read the access graph guide

09
Practice 06

Give Kubernetes RBAC
the same review

Datadog found 13% of EKS clusters run a node role with admin access, privilege escalation or broad data access.

KIEM finding for a ClusterRole that can create roles and role bindings. help.accuknox.com/getting-started/3.5-release

Do
  • Install the KIEM job on every cluster and schedule its scan.
  • Run the query for service accounts not connected to any workload.
  • List every role that can read Kubernetes secrets, and cut the ones that do not need it.
  • Treat permission to create roles and role bindings as critical.
Don't
  • Don't bind cluster admin to a workload service account.
  • Don't keep roles that no binding uses.
  • Don't assume cloud IAM reviews cover RBAC inside the cluster.
How AccuKnox closes the gap

KIEM ships 15 built in queries for RBAC risk, such as excessive privileges and unused roles, and draws each entity's connections as a graph. Set up KIEM
