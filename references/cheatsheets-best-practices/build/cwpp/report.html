Root causes

Four gaps let a runtime
attack run to the end

Detect, then react
A post attack tool kills the process after the alert fires. By then the attacker binary ran and could disable controls, delete logs or send data out.
No baseline of normal
Nobody recorded which processes, files and connections each container uses. So a cronjob and an attack look the same, and every rule stays in audit.
Evidence leaves with the pod
Attackers stay a median of 11 days before discovery. Yet 60% of containers live for 60 seconds or less, so the trail is gone when the hunt starts.
A flat cluster network
Kubernetes lets every pod reach every other pod by default. One compromised pod becomes the path to the database.

Sources. Dwell time from the Mandiant 2025 annual threat report, cloud.google.com. Container lifespan from the Sysdig 2025 Cloud Native Security and Usage Report, sysdig.com.

04
Practice 01

Learn what each
workload does first

The Discovery Engine records every process, file and network call per container, then writes that behavior as a policy you review.

App Behavior, process observability. help.accuknox.com/use-cases/app-behavior/

Do
  • Onboard each cluster and VM, then let discovery watch live traffic.
  • Review the File, Process and Network views for each workload in App Behavior.
  • Accept or discard each new discovered policy as cronjobs and code paths appear.
  • Keep policies in AUDIT for 2 to 3 weeks, until behavior holds steady and the policy is STABLE.
Don't
  • Don't write allow lists by hand from a design document.
  • Don't move a policy to BLOCK before it reaches STABLE.
  • Don't stop discovery after go live. Step 5 of the journey loops back to step 2.
How AccuKnox closes the gap

Discovery never stops, so the golden baseline keeps tracking real behavior for every container. Read the App Behavior guide

05
Practice 02

Harden workloads
with framework policies

KubeArmor ships hardening policies that map to CIS, MITRE ATT&CK, NIST, PCI DSS and STIG controls.

Runtime Protection policies with hardening tags. help.accuknox.com/use-cases/app-hardening/

Do
  • Deny package managers such as apt, apk and yum in production containers.
  • Block execution of any binary from /tmp/.
  • Protect the service account token when no process in the pod uses it.
  • Drop capabilities the app never uses, such as NET_RAW.
Don't
  • Don't leave admin, discovery and scan tools runnable in production pods.
  • Don't apply every hardening policy in BLOCK on day one. Run AUDIT first.
  • Don't treat an image scan as hardening. A clean image can still run an attacker binary.
How AccuKnox closes the gap

Pick a cluster and namespace in Runtime Protection, select the hardening policies, then apply and approve them. Browse the hardening policies

Practice 03

Block in the kernel,
not after the alert

KubeArmor enforces through LSMs such as AppArmor and BPF LSM, so a denied process never starts.

A blocked package manager run, result Permission denied. help.accuknox.com/use-cases/zero-trust/

Do
  • Move STABLE policies to BLOCK, so known behavior runs and the rest is denied.
  • Allow list the processes each container may run.
  • Allow network access only for the binaries that need it.
  • Let only named processes read credential and config files.
Don't
  • Don't rely on killing a process after an alert. The binary already ran.
  • Don't count on signatures. A deny by default policy rejects unknown malware too.
  • Don't expect enforcement on nodes without eBPF and LSM support. They drop to visibility only.
How AccuKnox closes the gap

Enforcement runs on each node with no sidecar and no inline proxy, and keeps working if the control plane is unreachable. Read the Zero Trust guide

Practice 04

Segment pod traffic
to stop lateral movement

Every pod can reach every other pod by default. A network policy limits each pod to the flows it needs.

Discovered network policies for a sample app. help.accuknox.com/use-cases/network-segmentation/

Do
  • Review the discovered ingress and egress policies for each app.
  • Segment by application tier, such as web to database only.
  • Segment by compliance scope, so regulated pods sit apart.
  • Approve each applied policy, because it waits in Pending until you do.
Don't
  • Don't treat a namespace as a network boundary. Pods on one node share Layer 2.
  • Don't write network rules before you see real traffic in App Behavior.
  • Don't let scan tools in a pod use ICMP to map the network.
How AccuKnox closes the gap

AccuKnox segments at the pod level and moves each policy from Pending to Active after approval. Read the segmentation guide

08
Practice 05

Stop miners and
lock system files

Of 50 compromised GCP instances, 86% ran cryptocurrency miners. A miner must download, write and run a binary, so block each step.

A blocked write to a system folder. help.accuknox.com/use-cases/vm-file-integrity/ Miner data from Google Cloud Threat Horizons, November 2021, services.google.com

Do
  • Block known miners such as xmrig and dero by name.
  • Block masscan, zgrab2, nmap and ntpdate, which miners use for recon and time sync.
  • Make /bin/, /sbin/, /usr/bin/ and /boot/ read only.
  • Cover config and credential paths, which PCI DSS, NIST and CIS expect FIM to watch.
Don't
  • Don't wait for an OOMKilled pod to tell you a miner runs.
  • Don't rely on a miner name list alone. Zero Trust policies also stop the next unknown miner.
  • Don't only alert on writes to system folders. Block them.
How AccuKnox closes the gap

In the documented test the miner exits with status 126, and the alert shows Permission denied. Read the cryptojacking guide

Practice 06

Keep evidence that
outlives the container

60% of containers live for 60 seconds or less. Capture process, file, network and syscall events before the pod is gone.

Runtime alerts timeline. help.accuknox.com/use-cases/forensics/ Lifespan data from Sysdig, 2025, sysdig.com

Do
  • Audit process, file, network and syscall events on critical workloads.
  • Audit every access to /etc/shadow, /etc/sudoers and /etc/pam.d/.
  • Block log deletion on critical components.
  • Forward alerts to Splunk, ELK or Rsyslog, and send high severity alerts to Slack.
Don't
  • Don't rely on node logs alone. They lose the pod and container context.
  • Don't ignore process enumeration with ps, pgrep or top.
  • Don't let alerts stay in the console. Route each one to a channel with an owner.
How AccuKnox closes the gap

Each alert records the cluster, pod, container, image, process, parent process, enforcer and result. Read the forensics guide
